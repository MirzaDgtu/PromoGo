# PromoGo Admin Web: продуктово-технический план

Статус: черновик для согласования  
Приоритет: раньше пользовательского мобильного приложения  
Дата: 2026-09-09

## 1. Решение и цель

Первым клиентским интерфейсом PromoGo должен стать административный web-сайт. Он нужен для подключения и сопровождения ритейлера: создания организаций и магазинов, управления доступом сотрудников, настройки программы лояльности, подключения касс и 1С, работы с клиентскими обращениями и просмотра аудита.

Мобильное приложение клиента остаётся отдельным продуктом и не входит в этот этап. Его API уже существует, поэтому мобильную разработку можно продолжить позже, не смешивая пользовательские сценарии с административными.

Этот документ не снимает feature freeze из `DEC-023`. До явного разрешения на разработку он является только планом. Реализация начинается после закрытия release gate либо после отдельного решения владельца проекта о новом цикле разработки.

## 2. Почему Admin Web раньше Mobile

- Без админки каждый новый магазин требует ручной работы разработчика или прямых API-вызовов.
- Админка закрывает onboarding, настройку и поддержку пилота; мобильное приложение само по себе этих задач не решает.
- Большая часть защищённого admin API, OIDC и RBAC уже реализована и протестирована.
- Web быстрее доставить и обновлять в пилоте, чем приложения через App Store и Google Play.
- Он даёт операционный контур для диагностики интеграции до масштабирования клиентской аудитории.

## 3. Три раздельных контура

Нельзя объединять их в одну сущность `User` или в одну авторизацию.

| Контур | Кто/что входит | Аутентификация | Назначение |
|---|---|---|---|
| Сотрудники | platform admin, администраторы ритейлера, управляющие, support | OIDC -> короткоживущий PromoGo staff token | Вход в Admin Web и административные операции |
| Клиенты программы | покупатели и их аккаунты/согласия | OTP, access/refresh session | Баланс, история, QR и уведомления; позже — Mobile |
| Технические субъекты | кассы, 1С, POS-коннекторы | store-scoped API keys и scopes | Машинные webhook/API-вызовы без доступа в Admin Web |

Админка может показывать разрешённые данные клиента для поддержки, но не должна авторизовываться как клиент. Касса или 1С не являются сотрудником и не получают staff token.

## 4. Текущее основание в backend

Уже доступны:

- OIDC-обмен через `POST /api/v1/staff/auth/oidc`;
- роли `platform_admin`, `retailer_admin`, `store_manager`, `support_viewer` и серверная permission-карта;
- создание организации и магазина, получение магазина;
- просмотр, создание и изменение membership сотрудников;
- поиск клиента в магазине и просмотр его транзакций;
- просмотр, изменение, история и rollback конфигурации лояльности;
- просмотр, однократная выдача и отзыв store API keys;
- аудит организации;
- OpenAPI-контракт и тест соответствия зарегистрированных маршрутов контракту.

До полноценной навигации и управления доступом в Admin Web не хватает как минимум:

1. `GET /api/v1/staff/me` — профиль, активные memberships, роли, scopes и вычисленные permissions.
2. `GET /api/v1/admin/organizations` — доступные текущему сотруднику организации; platform admin видит все, остальные только организации из memberships.
3. `GET /api/v1/admin/organizations/{orgID}/stores` — доступные магазины с учётом store-scoped memberships.
4. Пагинированного `GET .../stores/{storeID}/clients` с согласованными фильтрами, балансом и действующим маскированием ПДн.
5. Staff DTO, объединяющего membership с безопасными полями профиля (`display_name`, `email`), иначе UI показывает только числовой `staff_user_id`.
6. Согласованного staff enrollment: текущий create API требует сырой OIDC `external_subject`. Для пилота это может остаться управляемой операцией IdP-администратора, но такой сценарий нельзя называть self-service приглашением. Если нужен обычный invite/request-access flow, он проектируется отдельно с проверкой issuer/subject и без небезопасной привязки только по непроверенному email.

Эти API/DTO должны появиться до соответствующих экранов, быть описаны в OpenAPI и защищены теми же server-side RBAC/IDOR-проверками. Скрытие кнопки во frontend не является контролем доступа.

## 5. Предлагаемая архитектура frontend

### 5.1. Размещение и стек

- Каталог `web/admin` в этом репозитории: backend и Admin Web меняются вместе с одним OpenAPI-контрактом и общими CI-проверками.
- React + TypeScript в strict mode, сборка Vite.
- React Router для маршрутов.
- TanStack Query для server state, cache invalidation и единообразных loading/error состояний.
- React Hook Form + Zod для форм и runtime-валидации на границе API.
- Клиент и DTO генерируются из `docs/openapi/openapi.yaml`; вручную дублировать серверные типы нельзя.
- Лёгкий набор собственных UI primitives/design tokens. Подключение тяжёлой UI-библиотеки — отдельное обоснованное решение, а не автоматический выбор.

Версии зависимостей фиксируются lock-файлом после проверки актуальных стабильных релизов и совместимости. В плане намеренно не закреплены номера, которые быстро устаревают.

### 5.2. Развёртывание

Для пилота предпочтителен same-origin:

- `/` и assets обслуживают Admin Web;
- `/api/*` проксируется в Go backend;
- `/metrics` не публикуется через пользовательский ingress;
- неизвестный frontend route возвращает `index.html`, но `/api/*` никогда не попадает под SPA fallback.

Это упрощает CSP, cookies/headers и не требует широкого CORS. Если frontend и API будут на разных origins, разрешённые origins должны задаваться явной конфигурацией; wildcard с авторизацией запрещён.

### 5.3. Авторизация

1. Browser запускает OIDC Authorization Code Flow с PKCE через библиотеку выбранного IdP.
2. Полученный ID token передаётся в `POST /api/v1/staff/auth/oidc`.
3. Короткоживущий PromoGo access token хранится только в памяти приложения, не в `localStorage`.
4. После загрузки вызывается `/api/v1/staff/me`; на его результате строятся доступная навигация и выбранный org/store context.
5. При истечении токена выполняется тихое получение нового OIDC token, если IdP это разрешает, и повторный exchange; иначе — контролируемый возврат на login.

Конкретный IdP и его параметры остаются deployment-конфигурацией, как предусмотрено `DEC-004`.

## 6. Информационная архитектура и экраны

### 6.1. Общая оболочка

- Login и понятные состояния `no membership`, `disabled`, `session expired`.
- Переключатель организации и магазина, ограниченный memberships пользователя.
- Навигация строится по permissions, полученным от backend.
- Единый error boundary и страница ошибок с возможностью скопировать `X-Request-Id`.
- Desktop-first интерфейс, пригодный для планшета; русский язык первым, строки готовы к будущей локализации.

### 6.2. Первая поставка: Pilot Admin

1. **Обзор** — состояние настройки выбранного магазина: есть ли loyalty config, активный API key, последняя активность интеграции; без прямого доступа браузера к Prometheus.
2. **Организации и магазины** — список и карточки, создание в пределах permissions.
3. **Сотрудники и доступ** — имя/email, memberships, роль, scope, статус; создание, изменение, отключение с защитой от самоотключения и эскалации роли. Способ добавления нового сотрудника честно отражает согласованный enrollment: управляемый ввод IdP subject либо отдельно реализованный invite/request-access flow.
4. **Программа лояльности** — форма текущих правил, версия, история и rollback. До решения `Q-P0-068` изменения считаются немедленными, как в текущем API; UI явно предупреждает об этом.
5. **Клиенты** — пагинированный список/поиск, баланс, карточка и история операций. Маскирование ПДн определяется backend и ролью.
6. **API-ключи** — список, scopes, last used, expiry/revocation; plaintext нового ключа показывается ровно один раз с явным подтверждением сохранения.
7. **Аудит** — фильтруемый журнал значимых административных действий. Состав событий уточняется в `Q-P0-069`.

### 6.3. Вторая поставка: оборудование и интеграции

Сейчас отдельной модели кассы или соединения с 1С нет. `StoreAPIKey` — credential магазина, но не реестр оборудования. Нельзя делать UI-муляж поверх одних ключей.

Перед реализацией нужен короткий domain design/ADR с владельцем backend + интегратор 1С. Предлагаемое направление:

- `StoreDevice`: касса/POS-терминал, `store_id`, отображаемое имя, внешний ID, тип, статус, версия ПО, `last_seen_at`;
- `StoreIntegration`: тип (`1c`, `pos`), направление обмена, статус, безопасные metadata, время последнего успеха/ошибки;
- связь credential с конкретным device/integration либо явное обоснование store-wide credential;
- secrets сохраняются во внешнем secret store или как нераскрываемые ссылки, не возвращаются списковым API и не попадают в логи/audit payload;
- технические события показывают статус и request ID, но не сырые payload с ПДн.

Минимальные экраны после появления модели:

- список касс и их статусы;
- карточка кассы: внешний ID, scopes/credential, last seen, безопасная диагностика;
- список интеграций 1С/POS;
- карточка интеграции: endpoint/режим обмена, состояние, последняя успешная операция и обезличенная ошибка;
- ротация/отзыв credential;
- инструкция подключения и проверка фактического входящего webhook.

Кнопка «Проверить соединение» добавляется только если согласован реальный протокол проверки. При текущей входящей webhook-модели честнее показывать «последний успешный запрос», чем имитировать исходящее подключение к 1С.

## 7. Этапы реализации

### M0. Контракты и каркас

- согласовать этот план, снять/явно переопределить freeze для новой ветки работ;
- реализовать discovery/list API и staff DTO из раздела 4;
- согласовать управляемый staff enrollment или явно зафиксировать IdP-subject flow как ограничение пилота;
- обновить OpenAPI и parity/security тесты;
- создать `web/admin`, strict TypeScript, базовую структуру, generated API client;
- настроить OIDC login, `/staff/me`, org/store context и permission-aware shell;
- определить design tokens и обязательные UI-состояния.

Результат: сотрудник входит и видит только доступные ему организации, магазины и разделы.

### M1. Pilot Admin

- организации/магазины;
- сотрудники/RBAC;
- loyalty config, history, rollback;
- клиенты и транзакции;
- API keys;
- audit log;
- критические browser E2E-сценарии и CI.

Результат: новый пилотный магазин можно настроить и сопровождать без ручных curl/SQL операций.

Статус на 2026-10-29: сделано.
- Все экраны 6.2 (DEC-027…DEC-031).
- Решения по аудиту и списку клиентов (DEC-032, DEC-033).
- Компонентные тесты.
- Браузерные E2E критических сценариев с axe-проверкой каждого экрана
  (`web/admin/e2e/`).
- Образ admin-web (nginx + SPA, same-origin) и инструкция по выкладке и
  откату: `docs/admin-web-deployment.md`.

Из Definition of Done остаются:
- CI — в проекте пока не настроен;
- ручной security/regression review новой поверхности перед rollout.

### M2. Кассы и интеграции

- согласовать реальный контракт 1С и модель equipment/integration;
- добавить миграции, domain/service/repository/API и permissions;
- добавить UI оборудования, интеграций и диагностики;
- проверить credential isolation, cross-store IDOR и отсутствие secrets/ПДн в ответах и логах.

Результат: администратор понимает, что подключено к магазину, какими правами обладает и когда реально работало.

### M3. Production hardening

- CSP и остальные security headers;
- accessibility audit и keyboard-only сценарии;
- frontend observability без ПДн и токенов;
- bundle budget, кеширование immutable assets, rollback образа;
- regression, security review и обновление rollout/runbooks.

## 8. Проверки и CI

Frontend job должен выполнять установку по frozen lock-файлу, typecheck, lint, unit/component tests и production build. Отдельно:

- React Testing Library для поведения компонентов и доступности;
- MSW/contract fixtures, построенные из OpenAPI types;
- Playwright для login, смены org/store, изменения loyalty config, создания/revocation ключа и permission-denied сценариев;
- axe или эквивалент для автоматических accessibility checks;
- Go-тесты для новых API: negative, cross-org/store IDOR, store-scoped membership и PII masking;
- E2E с реальными PostgreSQL/Redis и тестовым OIDC issuer/verifier, а не production credentials;
- проверка, что generated client не расходится с OpenAPI.

Критические frontend ошибки должны показывать request ID пользователю и передавать его в диагностический контекст, не отправляя access token, телефон или API-key secret.

## 9. Definition of Done

Pilot Admin готов, когда:

- каждая роль видит только разрешённые организации, магазины, данные и действия;
- backend отклоняет те же запрещённые действия при прямом API-вызове;
- onboarding организации/магазина, выдача доступа, настройка правил и ключа выполняются из UI;
- клиентские данные маскируются согласно серверной политике;
- API-key plaintext нельзя повторно получить после закрытия one-time dialog;
- loading, empty, validation, conflict, forbidden, not found и server error состояния реализованы для всех страниц;
- UI доступен с клавиатуры, имеет корректные labels/focus и не зависит только от цвета;
- OpenAPI, Go baseline, frontend CI и критические Playwright-сценарии зелёные;
- deployment/rollback и эксплуатационные документы обновлены;
- human security/regression review новой поверхности завершён до rollout.

## 10. Не входит в этот этап

- Flutter/iOS/Android клиент и его product design;
- маркетинговый публичный сайт;
- кампании, сегментация, промокоды и расширенная аналитика;
- ручная коррекция баланса без отдельно утверждённого бизнес-процесса и audit policy;
- network/coalition balance до sign-off ADR;
- хранение произвольных логинов/паролей 1С в PromoGo без утверждённой secret-management модели;
- решения по юридическим вопросам, владельцам ПДн и срокам хранения.
