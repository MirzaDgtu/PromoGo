# Решения PromoGo

Здесь фиксируются только подтверждённые решения. Неотвеченные вопросы находятся
в [[Project Questions]].

## Принятые решения

### DEC-001 — 1С является источником событий, но не ядром лояльности

- Статус: принято
- Источник: [Idea.md](../Idea.md)
- Решение: PromoGo хранит собственный ledger, баланс и правила. 1С отправляет
  события продаж и повторяет их после сбоев.
- Следствие: идемпотентность внешних транзакций обязательна.

### DEC-002 — первый пилот ограничен одним магазином и механикой баллов

- Статус: принято для Phase 1
- Источник: [MVP-scope.md](../MVP-scope.md)
- Решение: cashback, штампы, уровни, акции, коалиции и multi-tenancy не входят в
  MVP.
- Следствие: текущая модель `client -> store` допустима для пилота, но решение о
  её миграции до нескольких магазинов остаётся открытым.

### DEC-003 — баланс изменяется через транзакционный ledger

- Статус: реализовано
- Источники: `internal/repository/postgres/ledger_repository.go`,
  `migrations/sql/00004_create_transactions.sql`
- Решение: начисление и списание атомарно создают запись транзакции и обновляют
  баланс; повторы возвращают результат исходной операции.

### DEC-004 — Organization как родитель Store, три независимых auth-контура

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-046`, `Q-P0-052`, `Q-P0-059`, `Q-P0-065`,
  `Q-P0-066`, `Q-P0-101`
- Контекст: до этого решения существовала только одна идентичность —
  `Client` (`store_id, phone`), создаваемая неаутентифицированно вебхуком
  1С. Не было способа клиенту авторизоваться самому, не было identity
  персонала, а API-ключ магазина был единственным неротируемым секретом.
- Решение:
  - Введена `Organization` — родитель `Store` (`stores.organization_id`).
    Существующие магазины при миграции `00013` переносятся в один
    `Default Organization`, single-store MVP продолжает работать без
    ручных операций.
  - Введены три полностью независимых контура идентичности, без общей
    таблицы `users`:
    1. **Клиент мобильного приложения** — `CustomerAccount` (глобальная,
       подтверждённая по телефону, не привязана к конкретному магазину) +
       `CustomerSession` (refresh-токены).
    2. **Сотрудник/администратор платформы** — `StaffUser` (идентичность
       по OIDC `sub`) + `StaffMembership` (роль в рамках Organization,
       опционально — конкретного Store).
    3. **1С/касса как service principal** — существующий `Store.APIKeyHash`
       (сохранён для обратной совместимости) + новая `store_api_keys`
       (несколько активных ключей, scopes, ротация).
  - `Client` остаётся участием в программе конкретного магазина;
    `clients.customer_account_id` (nullable) связывает его с
    `CustomerAccount` только после OTP-регистрации. Существующее поведение
    «неизвестный телефон при начислении создаёт `Client`» не изменилось —
    это по-прежнему не создаёт авторизованный `CustomerAccount`.
- Альтернативы: единая таблица `users` с полем `type` — отклонено, чтобы
  не смешивать разные модели авторизации (OTP-сессии, OIDC, API-ключи) и
  разные требования к ПДн в одной таблице.
- Последствия: `Store.APIKeyHash` теперь nullable (`00021`) — новые
  магазины, созданные через admin API, полагаются только на
  `store_api_keys`.

### DEC-005 — авторизация по permissions, а не по имени роли

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-066`
- Решение: `internal/domain/rbac.go` фиксирует 4 роли MVP
  (`platform_admin`, `retailer_admin`, `store_manager`, `support_viewer`) и
  раскрывает их в permissions (`organizations.manage`, `stores.read/manage`,
  `staff.manage`, `clients.read`, `transactions.read`,
  `loyalty_config.read/write`, `api_keys.read/rotate`, `audit.read`).
  Middleware `httpserver.RequireStaff` принимает permission и функцию
  разрешения scope (organization/store) из пути запроса; обработчики
  никогда не сравнивают имя роли напрямую.
- Следствие: `StaffPrincipal` (см. `internal/service/staffauth.go`)
  резолвится из БД на каждый запрос (не кэшируется в токене), поэтому
  отключение сотрудника/membership действует немедленно, а не только после
  истечения access-токена.

### DEC-006 — токены: golang-jwt/jwt/v5, отдельные типы claim, hand-rolled JWKS

- Статус: реализовано
- Дата: 2026-07-29
- Контекст: до этого решения в проекте не было ни одной JWT/OIDC
  зависимости (осознанно минимальный `go.mod`).
- Решение: добавлена `github.com/golang-jwt/jwt/v5` — как для
  клиентских access-токенов (HS256, подписаны и проверяются только самим
  сервисом), так и для верификации RS256 ID-токенов сотрудников. JWKS для
  OIDC получается и кэшируется вручную через `net/http`
  (`internal/auth/oidc.go`) — без `go-oidc`, чтобы не тащить discovery
  (issuer — просто одно конфигурационное поле). Клиентский и staff
  access-токен могут быть подписаны одним и тем же секретом: их
  взаимную неразличимость исключает claim `typ`
  (`customer_access`/`staff_access`), а не отдельные секреты.
  Refresh-токены и API-ключи — непрозрачные случайные значения
  (`crypto/rand`), в БД хранится только их SHA-256 хеш
  (`internal/auth/tokens.go`).
- Альтернативы: `coreos/go-oidc` (полный discovery) — отклонено как
  избыточное для одного сконфигурированного issuer; hand-rolled
  HMAC/RSA без библиотеки JWT — отклонено как более рискованное
  переизобретение формата токена.

### DEC-007 — OTP и refresh-токены: разное хранилище

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-047`, `Q-P0-102`
- Решение: OTP-вызовы (код, счётчик попыток, cooldown, rate limit по
  телефону/IP) живут только в Redis с TTL
  (`internal/service/otp_store.go`) — непройденный вызов должен просто
  исчезнуть без следа. Refresh-токены клиента хранятся в Postgres
  (`customer_sessions`, только хеш) — ротации/отзыву/детекции повторного
  использования нужно durable-состояние, которому нельзя доверять TTL-кеш.
  Код всегда хешируется (`internal/auth.HashOTP`, SHA-256) перед записью в
  Redis; при неудачной проверке инкрементируется счётчик попыток
  (`MaxAttempts`), после чего вызов удаляется. Ответ на
  `POST /auth/otp/request` одинаков независимо от того, существует ли уже
  `CustomerAccount` с этим телефоном — эндпоинт не может использоваться
  для перечисления аккаунтов.

### DEC-008 — жёсткая привязка Store API Key к scopes, dual-path совместимость

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-077`, `Q-P0-109`
- Решение: новая таблица `store_api_keys` (`00019`) хранит несколько
  одновременно активных ключей на магазин (`key_id`/`key_hash`, `scopes`,
  `expires_at`, `revoked_at`, `last_used_at`, `created_by`).
  `RequireStoreAPIKey` (`internal/httpserver/middleware.go`) сначала ищет
  ключ в `store_api_keys`, и только если не находит — проверяет legacy
  `stores.api_key_hash`. Legacy-ключ считается полностью доверенным (без
  ограничения по scope) — `requireScope` пропускает его без проверки,
  сохраняя прежнее поведение для магазинов, ещё не перешедших на
  мультиключевую схему. Plaintext ключа показывается ровно один раз при
  создании (`POST .../api-keys`), полный ключ никогда не логируется.
- Следствие: способ выпуска самого первого store API key для пилота
  по-прежнему требует ручной вставки в БД или предварительно созданного
  `platform_admin` через admin API — полноценный self-service bootstrap
  осознанно отложен (см. финальный отчёт после реализации).
