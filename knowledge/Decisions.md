# Решения PromoGo

Здесь фиксируются только подтверждённые решения. Неотвеченные вопросы находятся
в [[Project Questions]].

## Принятые решения

### DEC-001 — 1С является источником событий, но не ядром лояльности

- Статус: принято
- Источник: [Idea.md](../Idea.md)
- Решение: PromoGo хранит собственный ledger, баланс и правила. 1С отправляет
  события продаж и повторяет их после сбоев.
- Следствие: идемпотентность внешних транзакций обязательна.

### DEC-002 — первый пилот ограничен одним магазином и механикой баллов

- Статус: принято для Phase 1
- Источник: [MVP-scope.md](../MVP-scope.md)
- Решение: cashback, штампы, уровни, акции, коалиции и multi-tenancy не входят в
  MVP.
- Следствие: текущая модель `client -> store` допустима для пилота, но решение о
  её миграции до нескольких магазинов остаётся открытым.

### DEC-003 — баланс изменяется через транзакционный ledger

- Статус: реализовано
- Источники: `internal/repository/postgres/ledger_repository.go`,
  `migrations/sql/00004_create_transactions.sql`
- Решение: начисление и списание атомарно создают запись транзакции и обновляют
  баланс; повторы возвращают результат исходной операции.

### DEC-004 — Organization как родитель Store, три независимых auth-контура

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-046`, `Q-P0-052`, `Q-P0-059`, `Q-P0-065`,
  `Q-P0-066`, `Q-P0-101`
- Контекст: до этого решения существовала только одна идентичность —
  `Client` (`store_id, phone`), создаваемая неаутентифицированно вебхуком
  1С. Не было способа клиенту авторизоваться самому, не было identity
  персонала, а API-ключ магазина был единственным неротируемым секретом.
- Решение:
  - Введена `Organization` — родитель `Store` (`stores.organization_id`).
    Существующие магазины при миграции `00013` переносятся в один
    `Default Organization`, single-store MVP продолжает работать без
    ручных операций.
  - Введены три полностью независимых контура идентичности, без общей
    таблицы `users`:
    1. **Клиент мобильного приложения** — `CustomerAccount` (глобальная,
       подтверждённая по телефону, не привязана к конкретному магазину) +
       `CustomerSession` (refresh-токены).
    2. **Сотрудник/администратор платформы** — `StaffUser` (идентичность
       по OIDC `sub`) + `StaffMembership` (роль в рамках Organization,
       опционально — конкретного Store).
    3. **1С/касса как service principal** — существующий `Store.APIKeyHash`
       (сохранён для обратной совместимости) + новая `store_api_keys`
       (несколько активных ключей, scopes, ротация).
  - `Client` остаётся участием в программе конкретного магазина;
    `clients.customer_account_id` (nullable) связывает его с
    `CustomerAccount` только после OTP-регистрации. Существующее поведение
    «неизвестный телефон при начислении создаёт `Client`» не изменилось —
    это по-прежнему не создаёт авторизованный `CustomerAccount`.
- Альтернативы: единая таблица `users` с полем `type` — отклонено, чтобы
  не смешивать разные модели авторизации (OTP-сессии, OIDC, API-ключи) и
  разные требования к ПДн в одной таблице.
- Последствия: `Store.APIKeyHash` теперь nullable (`00021`) — новые
  магазины, созданные через admin API, полагаются только на
  `store_api_keys`.

### DEC-005 — авторизация по permissions, а не по имени роли

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-066`
- Решение: `internal/domain/rbac.go` фиксирует 4 роли MVP
  (`platform_admin`, `retailer_admin`, `store_manager`, `support_viewer`) и
  раскрывает их в permissions (`organizations.manage`, `stores.read/manage`,
  `staff.manage`, `clients.read`, `transactions.read`,
  `loyalty_config.read/write`, `api_keys.read/rotate`, `audit.read`).
  Middleware `httpserver.RequireStaff` принимает permission и функцию
  разрешения scope (organization/store) из пути запроса; обработчики
  никогда не сравнивают имя роли напрямую.
- Следствие: `StaffPrincipal` (см. `internal/service/staffauth.go`)
  резолвится из БД на каждый запрос (не кэшируется в токене), поэтому
  отключение сотрудника/membership действует немедленно, а не только после
  истечения access-токена.

### DEC-006 — токены: golang-jwt/jwt/v5, отдельные типы claim, hand-rolled JWKS

- Статус: реализовано
- Дата: 2026-07-29
- Контекст: до этого решения в проекте не было ни одной JWT/OIDC
  зависимости (осознанно минимальный `go.mod`).
- Решение: добавлена `github.com/golang-jwt/jwt/v5` — как для
  клиентских access-токенов (HS256, подписаны и проверяются только самим
  сервисом), так и для верификации RS256 ID-токенов сотрудников. JWKS для
  OIDC получается и кэшируется вручную через `net/http`
  (`internal/auth/oidc.go`) — без `go-oidc`, чтобы не тащить discovery
  (issuer — просто одно конфигурационное поле). Клиентский и staff
  access-токен могут быть подписаны одним и тем же секретом: их
  взаимную неразличимость исключает claim `typ`
  (`customer_access`/`staff_access`), а не отдельные секреты.
  Refresh-токены и API-ключи — непрозрачные случайные значения
  (`crypto/rand`), в БД хранится только их SHA-256 хеш
  (`internal/auth/tokens.go`).
- Альтернативы: `coreos/go-oidc` (полный discovery) — отклонено как
  избыточное для одного сконфигурированного issuer; hand-rolled
  HMAC/RSA без библиотеки JWT — отклонено как более рискованное
  переизобретение формата токена.

### DEC-007 — OTP и refresh-токены: разное хранилище

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-047`, `Q-P0-102`
- Решение: OTP-вызовы (код, счётчик попыток, cooldown, rate limit по
  телефону/IP) живут только в Redis с TTL
  (`internal/service/otp_store.go`) — непройденный вызов должен просто
  исчезнуть без следа. Refresh-токены клиента хранятся в Postgres
  (`customer_sessions`, только хеш) — ротации/отзыву/детекции повторного
  использования нужно durable-состояние, которому нельзя доверять TTL-кеш.
  Код всегда хешируется (`internal/auth.HashOTP`, SHA-256) перед записью в
  Redis; при неудачной проверке инкрементируется счётчик попыток
  (`MaxAttempts`), после чего вызов удаляется. Ответ на
  `POST /auth/otp/request` одинаков независимо от того, существует ли уже
  `CustomerAccount` с этим телефоном — эндпоинт не может использоваться
  для перечисления аккаунтов.

### DEC-008 — жёсткая привязка Store API Key к scopes, dual-path совместимость

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-077`, `Q-P0-109`
- Решение: новая таблица `store_api_keys` (`00019`) хранит несколько
  одновременно активных ключей на магазин (`key_id`/`key_hash`, `scopes`,
  `expires_at`, `revoked_at`, `last_used_at`, `created_by`).
  `RequireStoreAPIKey` (`internal/httpserver/middleware.go`) сначала ищет
  ключ в `store_api_keys`, и только если не находит — проверяет legacy
  `stores.api_key_hash`. Legacy-ключ считается полностью доверенным (без
  ограничения по scope) — `requireScope` пропускает его без проверки,
  сохраняя прежнее поведение для магазинов, ещё не перешедших на
  мультиключевую схему. Plaintext ключа показывается ровно один раз при
  создании (`POST .../api-keys`), полный ключ никогда не логируется.
- Следствие: способ выпуска самого первого store API key для пилота
  по-прежнему требует ручной вставки в БД или предварительно созданного
  `platform_admin` через admin API — полноценный self-service bootstrap
  осознанно отложен (см. финальный отчёт после реализации).

### DEC-009 — bootstrap-admin CLI закрывает chicken-and-egg первого platform_admin

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-067`, `Q-P0-109`
- Контекст: DEC-008 оставил открытым способ создания самого первого
  `platform_admin` `StaffMembership` — каждый admin-эндпоинт, способный
  выдать membership, сам требует уже существующего вызывающего с
  `staff.manage`, поэтому единственным путём была ручная вставка в БД.
- Решение: добавлена подкоманда `promogo bootstrap-admin
  --subject=... --email=... --name=... [--org-name=... | --org-id=...]`
  (`cmd/promogo/bootstrap_admin.go`), работающая напрямую поверх Postgres
  (`internal/service.BootstrapPlatformAdmin`) — без HTTP-сервера, Redis и
  admin API. Она резолвит `Organization` (по имени через новый
  `OrganizationRepository.GetByName`, либо по ID), создаёт/переиспользует
  `StaffUser` по `external_subject` и выдаёт org-wide `StaffMembership`
  с `Role = platform_admin`, переиспользуя тот же паттерн
  `ErrConflict`-как-идемпотентность, что и
  `StaffAuthService.resolveOrCreateUser` — повторный запуск с тем же
  subject+organization безопасен и не создаёт дублей. Если у пользователя
  уже есть org-wide membership с меньшей ролью, команда повышает её до
  `platform_admin` вместо того, чтобы молча сообщить об успехе, оставив
  неверную роль.
- Альтернативы: отдельный бинарь `cmd/promogo-bootstrap` — отклонено в
  пользу подкоманды единственного бинаря `promogo`, чтобы не плодить
  точки входа при отсутствии другой необходимости; auto-bootstrap по
  env-переменной при старте сервера — отклонено как более рискованное
  неявное поведение по сравнению с явным разовым CLI-вызовом оператора.
- Последствия и миграция: `Q-P0-067` и `Q-P0-109` закрыты полностью —
  bootstrap самого первого сотрудника платформы больше не требует ручной
  SQL-вставки.

### DEC-010 — keyset-пагинация для истории транзакций клиента

- Статус: реализовано
- Дата: 2026-07-29
- Связанные вопросы: `Q-P0-032`, `Q-P0-104`
- Контекст: `GET /api/v1/me/transactions` (`internal/httpserver/me.go`) уже
  существовал (добавлен в том же коммите, что и auth-контуры), но
  возвращал полную, неограниченную историю: мёрджил `ListByClient` по
  каждому `Client` клиента (по одному на магазин) в памяти и сортировал.
  Для активного клиента в нескольких магазинах список не ограничен ничем.
  Формулировка Q-P0-104 в backlog («роут отсутствует») была устаревшей —
  на самом деле не хватало именно пагинации, то есть Q-P0-032.
- Решение: добавлен `TransactionRepository.ListByClientIDs(ctx, clientIDs,
  limit, before *TransactionCursor)` — один SQL-запрос по
  `client_id = ANY(...)` с `ORDER BY created_at DESC, id DESC` и keyset-
  условием `(created_at, id) < (cursor)` вместо `OFFSET`. Эндпоинт
  принимает `?limit=&cursor=`, `limit` по умолчанию 20 (clamp 1..100,
  некорректное значение — молча дефолт), `cursor` — непрозрачная
  base64-строка `"<unix_nano>_<id>"`; неверный `cursor` — `400`. Ответ
  дополнен полем `next_cursor` (присутствует только если есть следующая
  страница) — обратно совместимо с прежней формой ответа.
- Альтернативы: `OFFSET`-пагинация — отклонена: под непрерывным потоком
  новых транзакций она пропускает или дублирует строки при перелистывании
  назад/вперёд, чего keyset-пагинация по возрастающему `(created_at, id)`
  не допускает.
- Последствия и миграция: `Q-P0-104` закрыт (эндпоинт был, только
  запись в backlog устарела); пагинационная часть `Q-P0-032` закрыта.
  Вопрос про максимальный период запроса (date-range) из `Q-P0-032` этим
  изменением не затронут и остаётся открытым.

### DEC-011 — QR: opaque versioned payload, Redis one-time token, store determined at scan time

- Статус: реализовано
- Дата: 2026-07-30
- Связанные вопросы: `Q-P0-049`, `Q-P0-050`, `Q-P0-106`, `Q-P0-107`
- Контекст: `Q-P0-046`/`Q-P0-052` уже установили, что клиент может числиться в
  нескольких магазинах через единый `CustomerAccount`; идентификация по
  телефону (`GET /api/v1/clients/lookup`) уже реализована, но не подходит
  как основной сценарий на кассе (кассир не должен вводить/видеть телефон
  каждый раз). Идентификация по карте сознательно не входит в эту задачу.
- Решение:
  - QR-payload — версионированная непрозрачная строка (`"v1." + token`),
    `token` — 32 случайных байта (`crypto/rand`, через существующий
    `auth.GenerateRefreshToken()`), base64url; не содержит телефон,
    `CustomerAccountID` или иной ПДн. Формат версионирован, чтобы будущая
    смена схемы была обнаружима без поломки уже выпущенных QR.
  - В Redis хранится только SHA-256 хеш токена
    (`auth.HashOpaqueToken`) → значение `customer_account_id`, с TTL
    `AntiFraudConfig.QRTTL` (default 2 минуты в development).
  - Consume атомарен: `GETDEL` по хешу — одна Redis-операция, гарантирующая
    ровно одно успешное потребление под конкурентным сканированием.
  - Между истёкшим (TTL), уже потреблённым и никогда не существовавшим
    токеном на уровне Redis нет различия (`GETDEL` возвращает `nil` во всех
    трёх случаях) — API намеренно возвращает один и тот же `410 Gone` для
    всех трёх, не раскрывая, какой из случаев произошёл. Отдельно
    валидируется только формат payload до обращения к Redis — ошибка
    формата это `400`, а не `410`.
  - Минимальный интервал повторного выпуска (`QRIssueCooldown`, default
    30s) — простой Redis-ключ с TTL (`EXISTS`), тот же паттерн, что уже
    используется для OTP resend cooldown (`internal/service/otp_store.go`).
    Отдельный `QRConsumeCooldown` ограничивает частоту `resolve-qr` со
    стороны одного store-принципала — защита от перебора токенов, не
    связана с одноразовостью самого токена.
  - QR универсален для платформы: сам payload не содержит `store_id`.
    Магазин определяется исключительно ключом кассы, которым вызван
    `POST /api/v1/clients/resolve-qr` — поэтому ни один QR ни при каком
    credential не может раскрыть данные другого магазина (IDOR
    структурно невозможен: в ответе всегда только `Client`/`Balance`
    вызывающего магазина).
  - После успешного обмена выданный `ClientID` действителен независимо от
    дальнейшей судьбы токена — истечение QR не отменяет уже выполненную
    идентификацию POS.
  - Backend не рендерит изображение QR — только payload; отрисовка QR
    остаётся на мобильном приложении.
- Альтернативы: подписанный JWT как QR-payload — отклонено: подпись без
  server-side состояния не даёт атомарной одноразовости, а хранить
  состояние всё равно пришлось бы в Redis, то есть JWT не убирает
  зависимость, только усложняет формат.
- Последствия и миграция: `Q-P0-049`/`Q-P0-050` закрыты; `Q-P0-106`
  закрыт полностью (OTP-часть закрыта раньше, см. DEC-007). Идентификация
  по карте остаётся открытой (не входила в эту задачу).

### DEC-012 — Refund: пропорциональные partial refunds, отрицательный баланс только через refund accrual

- Статус: реализовано
- Дата: 2026-07-30
- Связанные вопросы: `Q-P0-016`, `Q-P0-017`, `Q-P0-108`
- Контекст: `domain.TransactionRefund` и `transactions_type_check`
  допускали `refund` с самого начала (`00007`), но ни сервис, ни route, ни
  связь с исходной операцией реализованы не были.
- Решение:
  - `transactions.original_transaction_id` (nullable FK на `transactions`)
    обязателен для `type='refund'` и запрещён для остальных типов
    (`transactions_refund_reference_check`, `00022`).
  - Возврат разрешён только на `accrual` или `redeem`, не на другой
    `refund` — проверяется в Go внутри той же заблокированной
    (`SELECT ... FOR UPDATE`) DB-транзакции, что и запись возврата, а не
    CHECK/триггером, по аналогии с уже принятым в проекте стилем (бизнес-
    правила в Go, SQL — только для атомарности).
  - Частичные возвраты разрешены; накопленные `refunded_amount`/
    `refunded_points` хранятся прямо на исходной строке `transactions` и
    обновляются атомарно вместе с проверкой "не больше исходной суммы/
    points" — без гонки "прочитать сумму в сервисе → отдельно записать
    возврат".
  - Point delta считается пропорционально накопленной возвращённой сумме
    (`floor`), а последний refund, доводящий `refunded_amount` до полной
    суммы, забирает точный остаток баллов вместо округлённого значения —
    так округление никогда не оставляет невозвращённые/неудержанные
    баллы.
  - Refund исходного `accrual` уменьшает баланс (может увести в
    отрицательное значение — намеренно, чтобы клиент не сохранял баллы,
    начисленные за отменённую покупку). Refund исходного `redeem`
    возвращает списанные баллы (баланс только растёт).
  - `balances.balances_points_check CHECK (points >= 0)` снят полностью
    (`00022`) — неотрицательность обычного списания как и раньше
    гарантирует не CHECK, а guarded `UPDATE ... WHERE points + $2 >= 0` в
    `LedgerRepository`. Последующий `accrual` первым делом гасит
    отрицательный остаток — это следствие той же guarded-update формулы,
    отдельного кода не потребовалось.
  - Refund идемпотентен по тому же паттерну `(store_id, type,
    external_tx_id)` + `RequestFingerprint`, что accrual/redeem.
- Альтернативы: отдельная таблица `refunds` вместо расширения
  `transactions` — отклонено: `refund` уже является `TransactionType` и
  участвует в общей истории/пагинации (`/me/transactions`,
  `ListByClientIDs`) наравне с accrual/redeem, отдельная таблица потребовала
  бы дублировать эту интеграцию без выигрыша.
- Последствия и миграция: `Q-P0-016`/`Q-P0-017`/`Q-P0-108` закрыты для
  MVP-семантики (полный/частичный возврат, отрицательный баланс). Down-
  миграция `00022`, возвращающая `balances_points_check`, явно упадёт при
  наличии отрицательных балансов — это намеренно (см. комментарий в самой
  миграции), а не тихий no-op.

### DEC-013 — Anti-fraud: суточный лимит списания как rolling window, проверяемый атомарно с posting

- Статус: реализовано
- Дата: 2026-07-30
- Связанные вопросы: `Q-P0-079`, `Q-P0-107`
- Решение:
  - `AntiFraudConfig.DailyRedeemPointsLimit`/`DailyRedeemWindow` (config)
    ограничивают сумму реально списанных (после `MaxRedeemPercent` cap)
    points на `Client` за скользящее окно (по умолчанию 24 часа) — не
    календарные сутки, так как у `Store` пока нет timezone (см. открытый
    `Q-P1-...` по таймзонам).
  - Проверка выполняется внутри той же заблокированной DB-транзакции, что
    и запись redeem-транзакции (`LedgerRepository.PostRedeemChecked`):
    `SELECT ... FOR UPDATE` на строку баланса сериализует конкурентные
    списания одного клиента, затем сумма списанного за окно сравнивается
    с лимитом до вставки строки — гонка невозможна.
  - Refund не расходует суточный лимит: считается сумма только по
    `type = 'redeem'`, `refund`-строки в неё не входят.
  - Превышение — `domain.ErrDailyRedeemLimitExceeded` → HTTP `422` с
    машиночитаемым `code: "daily_redeem_limit_exceeded"`, отдельным от
    `insufficient balance`.
  - Вне `development` `DailyRedeemPointsLimit` обязателен и должен быть
    `> 0` — иначе `config.Load` завершается ошибкой при старте, по тому
    же паттерну, что `validateAuth` уже применяет к JWT-секрету.
  - QR issuance и QR consume имеют собственные, независимые от этого
    лимита cooldown/rate-limit защиты (см. DEC-011).
- Последствия и миграция: `Q-P0-107` закрыт для суточного лимита списания
  и QR-интервалов; более тонкий риск-скоринг (`Q-P1-055`) остаётся вне
  MVP.

### DEC-014 — SMS/FCM: провайдер-агностичные интерфейсы, fail-fast конфигурация вне development, outbox отложен

- Статус: реализовано (частично — см. последствия)
- Дата: 2026-07-30
- Связанные вопросы: `Q-P0-060`, `Q-P0-061`, `Q-P0-103`
- Контекст: `domain.SMSSender`/`domain.NotificationChannel` существовали
  только в виде dev-заглушек (`internal/notification/logsms`,
  `internal/notification/logchannel`); конкретный SMS-провайдер проектом
  ещё не выбран (см. `.claude/skills/add-notification-channel/SKILL.md`).
- Решение:
  - SMS: новый `internal/notification/httpsms` реализует `domain.SMSSender`
    поверх настраиваемого HTTP-шлюза (`SMSConfig`: `provider`, `endpoint`,
    `token`, `sender`, `timeout`) — без привязки к конкретному вендору,
    так как решение о провайдере ещё не принято. `provider=log` разрешён
    только в `development`; вне него — обязателен `provider=http` с
    заданными `endpoint`/`token`, иначе старт приложения завершается
    ошибкой.
  - FCM: `internal/notification/fcmchannel` реализует
    `domain.NotificationChannel` через официальный Firebase Admin SDK.
    Пустой `FCMConfig.CredentialsJSON` — фолбэк на `logchannel` только в
    `development`; вне него отсутствие credentials — ошибка старта
    (симметрично SMS).
  - Push-токены хранятся в новой таблице `customer_devices` (миграция
    `00023`), с revoke по невалидному/unregistered токену при отправке —
    самоочищающееся хранилище, без ручной чистки.
  - Доставка остаётся best-effort после commit транзакции — как и
    сегодняшние accrual-уведомления; сбой доставки никогда не откатывает
    уже записанную loyalty-транзакцию.
- Альтернативы: transactional outbox — рассмотрен и осознанно отложен как
  отдельная задача, чтобы не раздувать эту волну; см. `Q-P0-103-outbox`.
- Последствия и миграция: `Q-P0-103` закрыт для "какой канал первый и
  нужен ли outbox сейчас" (SMS/FCM оба реализованы как провайдер-
  агностичные каналы; outbox — нет, явно вынесен в отдельный бэклог-пункт
  `Q-P0-103-outbox`).

### DEC-015 — Transactional outbox для accrual/redeem/refund-уведомлений; батч-доставка FCM; QR claim/finalize/release

- Статус: реализовано
- Дата: 2026-09-09
- Связанные вопросы: `Q-P0-103-outbox` (закрыт этой задачей), `Q-P0-062`
  (остаётся открытым — локализация/deep link)
- Контекст: DEC-014 сознательно отложил transactional outbox. Аудит
  (`docs/audit-remediation-prompt.md`, Phase 3) потребовал: (1) убрать
  синхронный вызов FCM из пути accrual/redeem/refund, (2) не делать
  unbounded последовательный вызов на устройство, (3) не терять QR-токен
  из-за GETDEL до успешного завершения БД-работы, (4) throttling QR
  consume — по фактическому API-ключу, а не по store.
- Решение:
  - `notification_outbox` (миграция `00028`): `LedgerRepository.Post/
    PostRedeemChecked/PostRefund` принимают `*domain.
    NotificationOutboxEntry` (для `PostRefund` — builder-функцию,
    поскольку итоговый `pointsDelta` известен только под локом внутри
    метода) и вставляют строку в ТОЙ ЖЕ транзакции, что и сам ledger-write
    — уведомление ставится в очередь тогда и только тогда, когда
    транзакция закоммитилась. `LoyaltyService` больше не хранит
    `domain.NotificationChannel` и никогда не вызывает `Send` напрямую.
  - `internal/notifytemplates`: три шаблона (`accrual_credited`,
    `redeem_debited`, `refund_adjusted`) с `TemplateID`+`Version`,
    заменившие inline `fmt.Sprintf` на русском внутри `loyalty.go`.
    Локализация/deep link — не реализованы, остаются за `Q-P0-062`.
  - `internal/service.OutboxWorker`: поллинг + `ClaimBatch` (atomic
    `UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED)`, статус
    `processing` с lease-TTL для самовосстановления после краша воркера —
    паттерн, аналогичный `qrStore.claim`), bounded concurrency,
    экспоненциальный backoff, dead-letter после исчерпания попыток.
    Метрики — пока структурированные логи (Prometheus/OTel — предмет
    Phase 4, отдельной инфраструктуры метрик этот пакет не имеет).
  - `fcmchannel.Channel.Send`: переход с последовательного цикла
    (`Send` на устройство, до 5с каждый) на `SendEach` — SDK сам
    параллелит с ограниченной конкурентностью вместо unbounded
    последовательных вызовов; классификация невалидных токенов — из
    `BatchResponse.Responses[i].Error`.
  - QR (`qrStore`): `issue`/`checkConsumeCooldown` теперь `SET NX`
    (атомарный acquire, закрывает TOCTOU-гонку); `consume` (GETDEL)
    заменён на `claim`/`finalize`/`release` — токен не удаляется
    безвозвратно до успешного завершения БД-работы, при транзиентной
    ошибке возвращается в оборот, при бизнес-отказе (аккаунт не найден/не
    активен) — финализируется. Throttling-принципал consume-cooldown —
    `resolveQRConsumePrincipal` в httpserver: KeyID реального API-ключа,
    если он резолвится через `store_api_keys`, иначе store-scoped fallback
    для legacy `stores.api_key_hash`.
- Альтернативы: брокер сообщений (Kafka/RabbitMQ) вместо Postgres-таблицы
  — отклонён, избыточен для текущего объёма и добавляет отдельную
  инфраструктурную зависимость; Postgres уже source of truth для ledger.
- Последствия и миграция: `Q-P0-103-outbox` закрыт. Redis outage для
  security-sensitive контуров (OTP/QR/rate-limit) и POS-транзакций уже
  fail-closed (503) во всех местах, где используется Redis — см.
  `internal/ratelimit/middleware.go`, `otpStore`/`qrStore`; это
  подразумевает, что Redis-инцидент делает POS accrual/redeem/refund
  недоступным, пока 1С-очередь offline-retry не реализована и не
  протестирована end-to-end (1С-интеграция вне скоупа этого репозитория
  — см. `Q-P1-...` для 1С-контракта).

### DEC-016 — Phase 4 завершена: SLO/нагрузочное тестирование, backup/restore, разделение миграций

- Статус: реализовано (SLO/RPO-RTO — предложены, требуют подтверждения бизнесом)
- Дата: 2026-09-09
- Связанные вопросы: `Q-P0-083`, `Q-P0-085`, `Q-P0-088`, `Q-P0-091` (закрыт),
  `Q-P1-092` (закрыт), `Q-P1-093`
- Контекст: `docs/audit-remediation-prompt.md` Phase 4 требовал не только
  документацию, но воспроизводимые команды/CI-проверки с сохранённым
  результатом базового прогона по четырём направлениям: (1) workload-
  модель и измеримые SLO, (2) load/soak/dependency-failure тесты,
  проверяющие эти SLO, (3) RPO/RTO, backup/restore и реальный restore
  drill, (4) миграции отдельным deployment-шагом (expand/migrate/contract).
- Решение:
  1. **SLO** (`docs/slo.md`): workload-модель на основе заявленного в
     `MVP-scope.md` масштаба пилота (один магазин) с 5-10x запасом для
     кейса продажи следующим клиентам. Предложены (не согласованы с
     бизнесом): availability 99.5%/мес, POS webhook p95<300ms/p99<800ms,
     error rate <0.1% (429 явно исключён — rate limit по дизайну), outbox
     lag p95<30s.
  2. **Нагрузочные тесты** (`loadtest/`, k6 через `grafana/k6`, digest-
     pinned): `smoke.js` (быстрая проверка корректности), `load.js`
     (ramp 0→20→40 req/s, k6-`thresholds` = SLO из `docs/slo.md`),
     `soak.js` (15 минут на ~50% пиковой нагрузки), `dependency-failure.sh`
     (docker compose pause/unpause Redis и Postgres, проверка fail-closed).
     Новая подкоманда `promogo loadtest-seed` (по образцу
     `bootstrap-admin`) сеет магазин/API-ключ напрямую через репозитории —
     не полагается на устаревший raw-SQL из `.claude/skills/dev-stack/
     SKILL.md`, который разошёлся со схемой. CI: `.github/workflows/
     load-test.yml` (workflow_dispatch, не на каждый push — нагрузочный
     прогон стоит реальных минут).
  3. **Находка при первом прогоне `dependency-failure.sh`**: пауза
     Postgres-контейнера вызвала зависание запроса на неопределённое
     время (не 503, а полное отсутствие ответа) — у пути запроса не было
     контекстного дедлайна, в отличие от Redis (go-redis имеет
     дефолтные dial/read/write timeouts). Заморозка Postgres (SIGSTOP, не
     отказ) оставляет уже пуловое соединение висящим на чтении без каких-
     либо данных; несколько таких зависших горутин исчерпали бы
     `Postgres.MaxConns` и увели бы в отказ ВЕСЬ сервис, а не только
     запросы к замороженной зависимости. Исправлено: `requestTimeoutMW`
     (`internal/httpserver/middleware_timeout.go`) — 8с дедлайн на контекст
     каждого запроса; pgx v5 отслеживает отмену контекста у in-flight
     операций и принудительно закрывает соединение. После исправления:
     pause Postgres → 500 за ~8с (было: зависание), затем чистое
     восстановление. go-redis существующих таймаутов оказалось достаточно
     без изменений.
  4. **Реальный baseline-прогон** (2026-09-09, эта машина разработчика,
     Docker Desktop — не эталон production-железа): `smoke.js` — 100%
     success; `load.js` (после подъёма `ratelimit.accrual_*` лимитов для
     самого прогона — иначе один k6-контейнер как единственный caller
     упирается в per-IP/per-key лимит, рассчитанный на реальный пилотный
     трафик, а не на нагрузочный тест) — **все SLO выполнены с большим
     запасом**: accrual p95=13.18ms/p99=15.69ms, redeem p95=10.88ms/
     p99=13.24ms, balance p95=4.12ms (цели: 300/800/500ms), 0 ошибок;
     `dependency-failure.sh` — PASSED (Redis pause → 503×3, Postgres pause
     → 500×3 после исправления таймаута, оба восстановились чисто, паник
     не залогировано); `soak.js` (15 минут, ~50% пиковой нагрузки) — все
     SLO выполнены без деградации во времени (p95 даже немного ниже, чем в
     коротком `load.js`-прогоне — 10.93ms против 13.18ms, отсутствие
     утечки ресурсов под sustained-нагрузкой), `promogo_outbox_backlog`
     (снят каждые 60с через `/metrics`) слился с ~1895 (остаток от
     предыдущего `load.js`-прогона) до стабильных ~40 за 6 минут и
     оставался на этом уровне до конца прогона — backlog не растёт
     неограниченно. Полный transcript — см. `docs/load-test-baseline.md`.
  5. **Backup/restore/RPO-RTO** (`docs/backup-restore.md`): предложено (не
     согласовано с бизнесом) RPO 24ч (ежедневный `pg_dump`), RTO <30мин.
     Redis сознательно исключён — только эфемерное TTL'd состояние (OTP,
     rate-limit counters, QR-токены), не требует backup. **Реальный
     restore drill выполнен**: данные засеяны через настоящее приложение
     (`loadtest-seed` + 5 accrual + 1 refund), `pg_dump` (0.08с, 60KB) →
     `pg_restore` в новый пустой инстанс (0.51с) → сверка row count по 6
     таблицам (совпало точно) → `promogo migrate` + запуск приложения на
     восстановленной БД → `/readyz` 200, корректный баланс из
     восстановленных данных.
  6. **Миграции отдельным deployment-шагом** (`docs/deployment.md`): новая
     подкоманда `promogo migrate` (только применяет и выходит) и
     `internal/migrate.Verify` (только проверяет отсутствие pending
     миграций, ничего не применяет, лока не берёт).
     `AppConfig.SkipStartupMigrations` (default `false` — docker-compose
     не меняется) переключает `app.New` на `Verify` вместо `Run`, так что
     реплика, не подтвердившая актуальность схемы, отказывает в старте, а
     не обслуживает трафик против неё. **Проверено CI-джобом**
     `migration-deploy-model`: `promogo migrate` → две реплики параллельно
     против уже смигрированной схемы (`/readyz` 200 у обеих) → откат одной
     миграции → новая реплика отказывает в старте с понятной ошибкой →
     повторное применение. Та же последовательность прогнана вручную
     локально (throwaway-контейнеры) с идентичным результатом до переноса
     в CI. Expand/migrate/contract задокументирован; подтверждено, что все
     существующие миграции уже следуют expand-половине (каждый
     `DROP COLUMN` — в Down-секции отката, ни разу не применялся к
     колонке из более ранней миграции).
- Альтернативы: полноценный chaos-engineering инструмент (Toxiproxy,
  Chaos Mesh) вместо `docker compose pause` — отклонено для пилотного
  масштаба, избыточная инфраструктура; `docker compose pause`
  (фактический SIGSTOP контейнера) даёт даже более жёсткий тест
  (зависание, а не просто разрыв соединения), чем сетевой chaos-инструмент
  обычно эмулирует.
- Последствия и миграция: `Q-P0-091` и `Q-P1-092` закрыты. `Q-P0-083`,
  `Q-P0-085`, `Q-P0-088` — есть предложенные, протестированные ответы, но
  требуют подтверждения бизнесом (см. `knowledge/Project Questions.md`).
  Открыто: encryption backup-файлов, PITR/WAL-архивирование (нужны при
  росте за рамки одного пилотного магазина), alerting-правила поверх уже
  существующих метрик, retention данных с точки зрения 152-ФЗ (Phase 5).

- Альтернативы: рассмотрены в каждом ADR по отдельности (см. файлы) —

### DEC-018 — реальный pilot E2E тест закрывает Q-P0-095

- Статус: реализовано
- Дата: 2026-09-09
- Владелец: backend
- Связанные вопросы: `Q-P0-095` (закрыт)
- Контекст: продолжение [[#DEC-017]] — единственный пункт Phase 5,
  оставшийся открытым после ADR/legal-minimum/backlog-ревизии: реальный
  end-to-end тест, доказывающий полную цепочку пилота, а не только
  отдельные unit/route-тесты на fake-репозиториях
  (`internal/httpserver/testsupport_test.go`).
- Решение: `internal/e2e.TestPilotEndToEnd` — реальный Postgres+Redis,
  реальный запущенный `App`, реальные HTTP-запросы: 1С/POS accrual webhook
  → его же duplicate delivery (offline retry) → OTP-логин → видимость
  начисления в `/me/balance` → QR issue/resolve → списание →
  `/me/transactions` → возврат (с DEC-012's допустимым уходом баланса в
  минус) → duplicate delivery возврата → видимость возврата в
  `/me/balance`. Единственный обход: OTP-код не восстановим через API по
  дизайну (Redis хранит только хеш, `logsms` код не логирует) — тест
  подставляет capturing `domain.SMSSender` через новую `app.Option`
  (`app.WithSMSSender`, `internal/app/app.go`), которую production-код
  (`cmd/promogo/main.go`) не использует.
- Альтернативы: чисто black-box тест через уже собранный бинарник (как
  `loadtest/dependency-failure.sh`) был бы честнее по границе, но не может
  получить OTP-код никаким наблюдаемым способом — пришлось бы либо
  ослаблять хранение кода (неприемлемо), либо тест был бы неполным
  (пропускал бы OTP/QR-идентификацию). In-process запуск через `app.New` с
  одной точечной заменой SMS-отправителя выбран как минимально инвазивный
  компромисс.
- Последствия и миграция: в CI как `.github/workflows/ci.yml`'s
  `e2e-pilot`, на каждый push (не gated как `load-test.yml`, так как это
  корректностный, а не нагрузочный тест; занимает ~1с против реальных
  контейнеров). Проверено локально против одноразовых Docker-контейнеров
  до того, как закладывать в CI. `docs/e2e-testing.md` — как запускать
  локально. Phase 5 (per `docs/audit-remediation-prompt.md`) теперь
  закрыта во всех пунктах, кроме тех, что явно и обоснованно отложены в
  `knowledge/Project Questions.md`'s разделе 14.

### DEC-019 — Первый полный CI-прогон из чистого checkout: baseline и две реальные красные строки

- Статус: зафиксировано
- Дата: 2026-09-09
- Владелец: backend
- Связанные вопросы: `Q-P0-126` (новый), `Q-P0-127` (новый)
- Контекст: первый пункт management-level release gate после [[#DEC-018]]
  (Phase 5 инженерно закрыта) — "прогнать весь CI из чистого checkout"
  перед security/regression review и pilot rollout checklist, чтобы оба
  следующих документа опирались на подтверждённый baseline, а не на
  предположение "CI зелёный".
- Решение/находка: полный прогон всех 8 job'ов `.github/workflows/ci.yml`
  из свежего `git clone` на коммите `3e7c174`, версии инструментов и
  результаты каждого шага зафиксированы в
  `docs/ci-clean-checkout-baseline-2026-09-09.md`. 6/8 job'ов зелёные.
  2 красные, обе реальные и добавлены в `Project Questions.md` раздел 15:
  - `race` — воспроизводимая data race в тестовом double
    (`fakeStoreAPIKeyRepo` в `internal/httpserver/middleware_test.go`, без
    мьютекса, задета асинхронным `TouchLastUsed`) — не в production-коде.
  - `secret-scan` (gitleaks) — пример API-ключа в
    `docs/load-testing.md:46` (вывод `loadtest-seed`, коммит `82399bb6`),
    ложное срабатывание без allowlist-правила.
  Ни одна не исправлена в рамках этой сессии — по явной инструкции
  зафиксировать verdict без исправления новых проблем в том же коммите.
- Инцидент в процессе записи (не находка о продукте): первая попытка шага
  "verify a stale schema fails startup instead of serving silently" из
  job'а `migration-deploy-model` дала ложную тревогу — `promogo` не
  отказал в запуске против устаревшей схемы, а тихо сам её домигрировал и
  начал отвечать 200 на `/readyz`. Это выглядело как реальная регрессия
  ровно того гаранта, который этот CI job существует, чтобы доказывать.
  Причина оказалась не в продукте: команда, запускавшая этот шаг, забыла
  повторно экспортировать `PROMOGO_APP_SKIP_STARTUP_MIGRATIONS=true`
  (переменные окружения не переживают переход между отдельными вызовами
  Bash-инструмента в этой среде) — без неё `internal/app/app.go:85-101`
  корректно уходит в ветку `migrate.Run`, а не `migrate.Verify`. После
  чтения кода и повторного прогона с правильно выставленной переменной
  шаг прошёл штатно (`exit 1`, `pending migrations exist`). Записано
  явно, а не тихо отброшено, — до чтения кода это на несколько минут
  считалось реальной находкой.
- Также зафиксировано, но не заведено как P0/P1 (не блокирует ничего
  сейчас): `govulncheck` видит 3 известные уязвимости в
  `golang.org/x/crypto@v0.55.0` (`GO-2026-6355/6354/5932`), которые
  требуются транзитивно, но не достижимы из нашего кода — job зелёный
  по факту ("0 vulnerabilities" в вызываемом коде), это наблюдение о
  дереве зависимостей, а не о гейте.
- Последствия и миграция: `Q-P0-126`/`Q-P0-127` — owner backend, milestone
  "до merge-freeze перед пилотом" (см. `Project Questions.md` раздел 15).
  Следующие шаги release gate (материалы для security/regression review
  Phase 1–3, черновик pilot rollout/rollback checklist) теперь опираются
