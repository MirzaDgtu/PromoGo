# MVP — скоуп первого пилота

## Цель

Проверить сквозной флоу программы лояльности (1С → начисление баллов → клиент видит баланс в приложении → списание на кассе) на одном пилотном магазине минимальными силами. Результат — рабочий кейс для продажи следующим клиентам.

Полное описание продукта — см. `Idea.md`. Полный скоуп по фазам — см. `Full-scope.md`.

---

## Что входит в MVP

### 1. Backend API (Go + PostgreSQL)

- `POST /api/v1/transactions` — приём событий от 1С, начисление баллов
- `GET /api/v1/clients/{id}/balance` — баланс клиента
- `POST /api/v1/transactions/redeem` — списание баллов
- Только одна механика: **баллы** (% от суммы покупки)
- Идемпотентность по `transaction_id` (обязательна даже в MVP — без неё двойные начисления при повторной доставке webhook)
- Аутентификация webhook по API-ключу на магазин (HMAC можно отложить до Phase 2)
- Один режим сети: один магазин, без изолированных/коалиционных режимов

### 2. Мобильное приложение (Flutter)

- Регистрация и авторизация по номеру телефона (OTP)
- Текущий баланс баллов
- Динамический QR-код с TTL
- История транзакций (дата, сумма, начислено/списано)
- Push-уведомление о начислении баллов (Firebase FCM)

### 3. Web-конфигуратор (React) — минимальный

- Настройка % начисления и минимальной суммы покупки для бонуса
- Настройка правил списания (макс. % от чека, минимальный баланс, курс обмена баллов)
- Список клиентов с балансами (read-only, без сегментации)

### 4. Идентификация на кассе

- QR-код из приложения
- Номер телефона как fallback (ручной ввод кассиром)
- Регистрация нового клиента кассиром: телефон → SMS со ссылкой на приложение

### 5. Антифрод (минимум)

- Лимит на списание баллов в сутки на одного клиента
- Минимальный интервал между повторным сканированием QR

### 6. Интеграция с 1С

- Webhook в боевом контуре одного пилотного магазина
- Тестовая среда (sandbox) для отладки до запуска на боевых данных

### 7. Юридический минимум (не вырезается)

- Согласие на обработку персональных данных при регистрации (152-ФЗ) — обязательно по закону, как только начинаем собирать телефоны клиентов
- Базовая политика конфиденциальности

## Что сознательно НЕ входит в MVP

| Вырезано | Причина |
|---|---|
| Тиры (Bronze/Silver/Gold) | Усложняет движок начисления, не критично для проверки гипотезы |
| Штампы (punch card), кэшбэк | Дополнительные механики — добавляются после валидации базовой |
| Акции и временные промо | Требуют отдельного UI в конфигураторе |
| Реферальная программа, геймификация | Влияют на рост базы, но не на проверку core-флоу |
| Привязка физической карты | QR + телефон достаточно для пилота |
| Несколько магазинов / режимы сети | Пилот — один магазин |
| Аналитический дашборд (RFM и т.д.) | Нужен для продажи следующим клиентам, не для пилота |
| Маркетинговые рассылки (push/SMS-кампании) | Кроме обязательного push о начислении |
| Apple/Google Wallet, веб-версия, офлайн-QR | Удобства, не блокируют проверку гипотезы |
| Multi-tenancy / биллинг платформы | Решается после получения первых платящих клиентов |
| HMAC-подпись webhook, расширенный антифрод | API-ключа достаточно для одного доверенного пилота |

## Команда и сроки (ориентировочно)

- 1 backend-разработчик (Go)
- 1 mobile-разработчик (Flutter)
- 1 frontend-разработчик (React) — может совмещаться с backend на старте
- Специалист по 1С на стороне пилотного ритейлера для интеграции
- Срок: ~2–3 месяца при команде 2–3 человека

---

## Критерии успеха пилота

- Корректное начисление/списание баллов без расхождений с данными 1С
- N зарегистрированных клиентов через приложение за первый месяц (целевое число согласовать с ритейлером)
- Обратная связь от ритейлера и кассиров для доработки перед продажей следующим клиентам
- Готовый кейс (метрики, отзыв) для использования в продажах
